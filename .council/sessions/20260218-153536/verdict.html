Winning Direction: The council has decided to proceed with the recommendations outlined in oc-big-pickle’s proposal, with key modifications derived from the critiques and votes. This direction prioritizes leveraging existing code, addressing critical integration gaps, and implementing pragmatic enhancements for a small team.

Key Modifications:

The following adjustments will be incorporated into the winning direction:

  • Question 2 (Classification — LLM in the Loop?): Introduce a lightweight GLM-5 pre-check for variables with an initial classification confidence between 0.5 and 0.79 to proactively confirm or infirm the pattern classification. This provides an early, no-cost quality gate for borderline cases.
  • Question 3 (Pattern Optimization): Reduce the scope of the “battue” (empirical validation) from 500 to 100 randomly sampled variables. This provides sufficient directional data for pattern calibration without an excessive upfront time investment.

Final Recommendation:

The final, synthesized plan for the operational architecture of the cleaning pipeline is as follows:

  1. Question 1: Orchestrator Role — Activate true batching with accumulation buffer.
    • The orchestrator.py will be refactored to explicitly separate classification and processing into two passes. After all variables are classified, Tier 2 variables will be grouped by similarity using the existing create_batches() function and processed in batches of 10-20, significantly reducing API calls. Tier 1 variables will be processed instantly, and Tier 3 individually.
  2. Question 2: Classification — Keep deterministic with LLM-light pre-check for borderline cases.
    • The core classification process will remain 100% deterministic (stats-only). However, for variables where the deterministic classifier has a confidence score between 0.5 and 0.79 (currently slated for Tier 2 anyway), a lightweight, free GLM-5 LLM will be used to confirm or adjust the pattern classification. The Tier 1 confidence threshold will be slightly lowered to 0.85 to be more conservative in initial deterministic assignments.
  3. Question 3: Pattern Optimization — Perform a focused battue on 100 variables.
    • An empirical validation (“battue”) will be conducted on 100 randomly sampled variables (stratified by survey). This effort (estimated 1 day) is crucial to calibrate existing patterns and identify missing ones. A simple CSV will be used for manual annotation. The primary metric will be the Tier 1 match rate (automatic vs. manual classification), with a target of ≥50%. If the rate is <40%, deeper investigation into missing patterns is warranted.
  4. Question 4: Naming Strategy — Use codebook labels for Tier 1, LLM for Tier 2, with robust fallback.
    • For Tier 1 variables, the _generate_clean_var_name() function will be modified to derive names from the var_label found in the codebook, converting it to snake_case and applying appropriate prefixes (ses_, op_, behav_). A robust fallback mechanism will ensure that if var_label is missing, the raw variable name is used. Tier 2 variables will continue to be named by the GLM-5 LLM, ensuring consistency.
  5. Question 5: Validation — Connect existing CleanValidator after assembly, then LLM-light for Tier 1 failures.
    • The existing CleanValidator will be integrated into the orchestrator.py to run after all variables have been processed and clean.py has been assembled. This pass will perform static (AST, duplicate assignments) and dynamic (types, ranges) validation. If a Tier 1 generated code fails this initial validation, an additional lightweight (free GLM-5) semantic check will be performed specifically for that variable to catch subtle errors like inverted mappings, before escalation.
  6. Question 6: Escalation Strategy — Automatic, confidence-based with circuit-breaker.
    • Escalation will be automatic upon any validation failure.
    • A confidence-based shortcut will be implemented: if the initial Tier 1 classification confidence is below 0.85, the variable will skip Tier 1 processing and go directly to Tier 2 to avoid wasted effort on highly uncertain cases.
    • When escalating, the detailed reason for the validation failure and the incorrect_code generated by the previous tier will be transmitted to the next tier for better context.
    • A circuit-breaker will limit escalations to a maximum of 2 attempts per variable (T1 → T2 → T3). If a variable fails validation after the Tier 3 attempt, it will be marked needs_review=True in status.json, along with the detailed error.

Dissenting Views:

While the primary direction is clear, oc-kimi-k2.5-free expressed a preference for:

  • Orchestrator Structure (Q1): An explicit two-pass structure over an accumulator approach, believing it to be cleaner and more testable.
  • Classification (Q2): Keeping classification 100% deterministic and postponing the empirical battue, arguing that GLM-5’s free nature makes early pattern optimization less urgent.
  • Escalation (Q6): A more restrictive escalation (max 1 escalation) and maintaining the Tier 1 threshold at 0.8, rather than increasing it.
