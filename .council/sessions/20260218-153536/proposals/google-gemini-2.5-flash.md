**Summary**
This recommendation addresses the operational architecture and LLM integration within the `survey-cleaner` pipeline. The core focus is on enhancing the Tier 2 batching, improving classification accuracy and variable naming, integrating a lightweight LLM into validation for Tier 1 outputs, and establishing a robust tier escalation strategy to ensure pipeline resilience and data quality for a small team.

---

**Recommendation**

**1. Orchestrator Role: Option B — Garder la boucle séquentielle mais activer le vrai batching**
For a small team, this is the most pragmatic approach. It leverages the existing sequential structure while directly addressing the critical issue of Tier 2 batching. Instead of a complete architectural overhaul to an event-driven system, accumulate Tier 2 variables in a temporary buffer and flush them for processing when the batch size (e.g., 10-15 variables) is met or when the pipeline reaches its natural end for the current survey.

**2. Classification: Option B — Ajouter un LLM ultra-léger (GLM-5 gratuit) pour les variables à confiance 0.5–0.79**
Introducing a lightweight LLM for borderline cases (confidence 0.5-0.79) significantly improves classification accuracy without incurring additional costs. These variables are already slated for Tier 2; a pre-check can prevent misclassifications (false Tier 1s) and ensure more appropriate tiering, making the overall pipeline more efficient.

**3. Pattern Optimization: Oui, ça vaut la peine d'optimiser les patterns**
**A) Vaut-il la peine d'investir ce temps?** Oui. While Tier 2 is free, maximizing Tier 1 usage (which is deterministic and immediately processed) reduces LLM dependency, improves transparency, and decreases downstream validation and potential escalation costs. It's a foundational improvement for long-term robustness.
**B) Comment structurer cette battue?**
*   **Échantillonnage:** Une stratégie d'échantillonnage aléatoire des 500 variables est suffisante pour une première passe. Cela couvrira une bonne diversité de cas réels.
*   **Outil d'annotation:** Un simple fichier CSV avec une colonne `manual_classification` à remplir manuellement est le plus simple.
*   **Mesure du gain:** Comparer le taux de Tier 1 et le nombre d'escalades/erreurs avant et après l'optimisation des patterns.
**C) Seuil de taux Tier 1:** Viser ≥60% comme un seuil initial. Si après optimisation, le taux est significativement en dessous, il faudrait réévaluer l'approche des patterns.

**4. Variable Naming: Option C — Nommage basé sur le label du codebook plutôt que le nom brut**
This option will lead to significantly more readable and semantically meaningful variable names for Tier 1, aligning better with the quality of names generated by Tier 2. It removes the ambiguity and truncation issues of raw names.

**5. LLM in Validation & Integration:**
**A) Intégration dans l'orchestrateur:** Intégrer la validation **après chaque variable individuellement**. This allows for immediate feedback and an instant retry/escalation mechanism, preventing late-stage discovery of errors that would require reprocessing the entire `clean.py` script.
**B) LLM dans la validation:** **Option LLM-light (GLM-5 gratuit) pour les variables Tier 1 seulement.** This is a critical addition. Since Tier 1 is deterministic and has no LLM involvement, it's susceptible to subtle semantic errors (e.g., inverted scales). A quick LLM check here acts as an intelligent guardrail, catching common pitfalls before they propagate.

**6. Validation Failure & Escalation:**
**A) Escalade automatique:** L'escalade devrait être **automatique**. If validation fails, the current tier's output is demonstrably incorrect or insufficient.
**B) Information à transmettre:** Transmettre **les deux**: le `reason` détaillé de l'échec de validation et le `code incorrect généré` par le tier précédent. Cela fournit un contexte complet au tier supérieur pour diagnostiquer et corriger le problème.
**C) Éviter les boucles infinies:** Implémenter un **nombre maximum d'escalades par variable** (e.g., 2 tentatives après la classification initiale, donc max 3 passes total: T1->T2->T3). Si une variable échoue après la dernière tentative (Tier 3), marquez-la `needs_review=True` et stockez le code d'erreur détaillé.
**D) Augmenter le seuil de confiance Tier 1:** Oui, augmenter légèrement le seuil de confiance Tier 1 (e.g., 0.8 -> 0.85) est justifié. Cela réduira les "faux positifs" à l'entrée de Tier 1, diminuant le volume de validation-échec-escalade et améliorant l'efficacité globale.

---

**Trade-offs**

*   **Option B (Orchestrator):**
    *   **Pros:** Minimal change to existing architecture, direct fix for batching, easier to implement and debug for a small team.
    *   **Cons:** Not as fundamentally "clean" as an event-driven system, could become more complex if many new tiers or complex dependencies are added later (low risk for current project scope).
*   **Option B (Classification):**
    *   **Pros:** Improved classification accuracy for borderline cases, reduced false Tier 1s, zero additional cost (GLM-5 is free).
    *   **Cons:** Introduces a very slight latency for a subset of variables during classification.
*   **Pattern Optimization:**
    *   **Pros:** Increases free, deterministic processing, reduces reliance on LLMs, improves transparency, strengthens foundation.
    *   **Cons:** Requires manual effort (2-4 days) upfront.
*   **Option C (Naming):**
    *   **Pros:** More readable and semantically consistent variable names, improved data quality.
    *   **Cons:** Requires careful implementation of snake_case conversion and prefixing logic for Tier 1.
*   **LLM-light in Validation (Tier 1):**
    *   **Pros:** Catches semantic errors early in the cheapest tier, critical quality gate, zero additional cost.
    *   **Cons:** May introduce occasional false positives from the LLM that need manual override (rare with simple prompts).
*   **Automatic Escalation:**
    *   **Pros:** Robust error handling, ensures problematic variables are eventually handled by higher-capability tiers, reduces manual intervention.
    *   **Cons:** Can increase overall processing time for difficult variables, requires careful implementation of retry limits.

**Implementation Sketch**

1.  **Orchestrator Refactor (Q1):**
    *   Introduce a `tier2_batch_buffer = []` in `orchestrator.py`.
    *   When a variable is classified as Tier 2, append it to `tier2_batch_buffer`.
    *   Modify the processing loop:
        *   If `len(tier2_batch_buffer) >= BATCH_SIZE` (e.g., 15) or end of variables: call `tier2_batch.process(tier2_batch_buffer)` and clear buffer.
    *   Ensure any remaining variables in `tier2_batch_buffer` are processed at the end of the pipeline.

2.  **LLM in Classification (Q2):**
    *   In `pattern_classifier.py`, after initial classification and confidence calculation:
        *   If `0.5 <= confidence < 0.8`: Call `llm_processors/glm5_classifier.py` with variable context to confirm/infirm pattern classification. Adjust `tier` and `pattern_id` based on LLM output.

3.  **Pattern Optimization (Q3):**
    *   **Setup:** Create a script to extract random 500 variables (raw name, data sample, codebook label) into a CSV.
    *   **Annotation:** Manually annotate the CSV with the correct `tier`, `pattern_type`, and `clean_var_name`.
    *   **Analysis:** Compare automatic classification with manual. Adjust `pattern_engine/patterns/` and confidence thresholds in `pattern_classifier.py`.

4.  **Variable Naming (Q4):**
    *   Modify `_generate_clean_var_name()` in `orchestrator.py`:
        *   For Tier 1: Use `var_label` from codebook, convert to snake_case, then apply pattern-based prefix (`ses_`, `op_`). Prioritize `var_label` over `raw_name`.

5.  **Validation Integration & LLM (Q5):**
    *   In `orchestrator.py`, after each variable's code generation (Tier 1, Tier 2, Tier 3):
        *   Call `validation/validator.py` with the generated code and variable context.
        *   Specifically for Tier 1: if initial validation passes, call `llm_processors/glm5_validator.py` with the generated Tier 1 code and original variable context for semantic consistency check.

6.  **Escalation Strategy (Q6):**
    *   Introduce a `retry_count` for each variable in `status.json`.
    *   In `orchestrator.py`:
        *   If `validation/validator.py` or `llm_processors/glm5_validator.py` fails:
            *   Increment `retry_count`.
            *   If `retry_count < MAX_RETRIES` (e.g., 2):
                *   Determine next `tier` (T1->T2, T2->T3).
                *   Pass validation `reason` and `incorrect_code` to the next tier's processing function.
                *   Re-process the variable in the next tier.
            *   Else (max retries reached):
                *   Mark variable `needs_review=True` in `status.json`.
                *   Store validation `reason` and `incorrect_code`.
    *   Adjust `pattern_classifier.py` to use a slightly higher Tier 1 confidence threshold (e.g., 0.85).
